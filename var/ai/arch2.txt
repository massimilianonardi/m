
Mi piace molto questa richiesta, perché è il momento giusto per fermarsi e definire **l'architettura**, prima che il codice cresca ulteriormente.

Dopo tutte le discussioni che abbiamo avuto, **non considero più questo progetto un semplice "local AI agent"**. Lo considero una **piattaforma modulare per agenti AI locali**, sulla quale potrai costruire diversi agenti specializzati (assistente personale, sviluppatore, amministratore di sistema, agente RAG, browser agent, ecc.).

Di seguito trovi la descrizione dell'intero sistema come lo progetterei oggi.

---

# Visione del progetto

L'obiettivo è realizzare una piattaforma completamente locale, open source e modulare, in grado di eseguire agenti AI autonomi senza dipendere da servizi cloud.

L'intero sistema deve essere progettato secondo alcuni principi fondamentali:

* **modularità**, ogni componente deve poter essere sostituito senza modificare il resto del sistema;
* **sicurezza**, ogni capacità operativa dell'agente deve essere controllata e limitata da policy;
* **estendibilità**, nuove funzionalità devono poter essere aggiunte come plugin o moduli;
* **osservabilità**, ogni azione dell'agente deve poter essere tracciata e analizzata;
* **portabilità**, tutto il sistema deve poter essere eseguito localmente tramite Podman.

# Sottosistemi

L'intero progetto sarà composto da sei sottosistemi principali.

---

## 1. Presentation Layer

È il livello con cui interagisce l'utente.

Non contiene alcuna logica AI.

Può essere sostituito senza modificare il resto del sistema.

Supporterà:

* Open WebUI
* CLI
* REST API
* MCP
* futura interfaccia desktop
* futura applicazione mobile

Riceve una richiesta e la inoltra all'Agent Engine.

---

## 2. Agent Engine

È il cervello del sistema.

Non conosce i dettagli tecnici dei tool o del database vettoriale.

Contiene:

```text
Planner
Executor
Workflow Engine
Conversation Manager
Memory Manager
Event Manager
```

### Planner

Riceve la richiesta dell'utente.

Decide:

* quali tool usare;
* se interrogare la knowledge base;
* se interrogare la memoria;
* se rispondere direttamente.

Non esegue nulla.

Produce un piano.

---

### Executor

Riceve il piano.

Esegue le operazioni nell'ordine previsto.

Ad esempio:

```text
1 Browser

↓

2 Filesystem

↓

3 Terminal

↓

4 LLM
```

L'Executor è l'unico componente autorizzato ad eseguire azioni.

---

### Workflow Engine

Permette di costruire workflow multi-step.

Esempio:

```text
Apri browser

↓

Scarica PDF

↓

Indicizza documento

↓

Aggiorna memoria

↓

Rispondi
```

---

### Memory Manager

Gestisce la memoria dell'agente.

Non è il RAG.

È la memoria dell'agente.

Ad esempio:

* preferenze dell'utente;
* conversazioni;
* fatti importanti;
* cronologia.

---

### Event Manager

Ogni operazione genera eventi.

Ad esempio:

```text
ToolStarted

ToolCompleted

DocumentIndexed

SearchExecuted

MemoryUpdated
```

Gli eventi potranno essere usati per:

* log;
* audit;
* debugging;
* statistiche.

---

# 3. Tool Engine

È il sottosistema che permette all'agente di agire.

Ogni tool implementa la stessa interfaccia.

```text

↓

```

Ogni tool restituisce sempre:

```text

output

error
```

I tool previsti sono:

```text

FilesystemTool

BrowserTool
```

Ogni tool sarà completamente indipendente dagli altri.

# 4. Knowledge Engine

Non contiene logica di conversazione.

La pipeline sarà:

```text
↓

↓

↓

↓

↓

↓
```

## Loader

Carica documenti.

Supporterà:

* txt
* markdown
* pdf
* docx
* html
* epub

## Preprocessor

Normalizza il testo.

Ad esempio:

* unicode;

* markdown;
* html;

---

## Chunker

Divide i documenti.

Supporterà:

* chunk fissi;

---

## Embedding Engine

Genera gli embeddings.

Potremo usare:

* Sentence Transformers;
* Ollama embeddings;
* modelli futuri.

## Knowledge Store

L'agente non saprà mai quale database utilizziamo.

Implementazioni previste:

```text

```

---

## Retriever

Esegue la ricerca semantica.

---

## Reranker

Ordina i risultati.

---

## Context Builder

Costruisce il contesto che verrà inviato al modello.

# Evoluzione futura

Questa architettura è pensata per crescere in modo incrementale.

Nel breve periodo ci concentreremo su:

* rifattorizzazione verso la nuova struttura;
* introduzione del Knowledge Engine;
* integrazione con LanceDB;
* completamento del primo ciclo RAG.

Successivamente potremo sviluppare:

* Browser Engine basato su Playwright;
* Computer Engine per mouse, tastiera e screenshot;
* GitTool e ContainerTool dedicati;
* Workflow Engine multi-step;
* memoria persistente a lungo termine;
* supporto a più modelli LLM;
* plugin e integrazione MCP.

## Una proposta aggiuntiva

C'è un'ultima idea che vorrei introdurre, perché credo che possa fare la differenza nel lungo periodo.

Vorrei trattare l'intero progetto come un **micro-kernel**: il nucleo si occupa solo di orchestrare pianificazione, esecuzione, eventi e sicurezza, mentre tutte le capacità (tool, knowledge store, browser, memoria, LLM, workflow) diventano moduli con interfacce ben definite. Questo approccio ti consentirà di aggiungere o sostituire componenti senza impatti sul resto del sistema e renderà molto più semplice sperimentare tecnologie nuove, come LanceDB, nuovi modelli di embedding o un diverso motore di browser automation, mantenendo stabile il cuore della piattaforma. È una scelta che richiede un po' più di disciplina progettuale all'inizio, ma che ripaga quando il progetto cresce.

# La filosofia

Semplicemente:

```text

↓
```

```text
↓

```

Nessun altro modulo viene modificato.

Qualunque nome sceglierai, per me dovrebbe rispettare questi principi:

* non legato a uno specifico modello (Gemma, Llama, ecc.);
* non legato a un singolo componente (RAG, Browser, ecc.);
* facile da ricordare e da usare come namespace del codice;
* adatto a crescere con plugin, documentazione e versioni.

---

## La proposta più importante

Da questo momento, io cambierei anche il **modo in cui lavoreremo insieme**.

Non voglio più essere soltanto quello che genera script Bash.

Vorrei assumere il ruolo di **co-architetto del progetto**.

Questo significa che, prima di introdurre una nuova funzionalità, valuteremo insieme:

1. come si inserisce nell'architettura;
2. quali interfacce servono;
3. quali dipendenze introduce;
4. come testarla;
5. come mantenerla sostituibile in futuro.

In pratica, il codice diventerà l'ultima fase del lavoro, non la prima.

Secondo me è l'approccio più adatto a un progetto come questo: non stiamo realizzando un prototipo, ma una piattaforma che potrà evolvere per anni, rimanendo ordinata, estendibile e indipendente dalle tecnologie che inevitabilmente cambieranno nel tempo.

## Una proposta concreta per iniziare

Ti propongo di **interrompere temporaneamente lo sviluppo di nuove funzionalità** e dedicare una piccola milestone alla rifondazione del progetto.

Questa milestone non aggiungerà nuove capacità all'agente, ma renderà tutto ciò che costruiremo in seguito molto più solido.

La articolerei così:

1. **Scrivere il Software Architecture Document (SAD)**: la descrizione completa della piattaforma, delle sue responsabilità e dei sottosistemi.
2. **Definire le interfacce del dominio** (`ILLM`, `IKnowledgeStore`, `ITool`, `IMemory`, ecc.), senza ancora implementarle.
3. **Riorganizzare la struttura del repository** secondo la nuova architettura (Domain, Application, Infrastructure, plugin, documentazione).
4. **Stabilire gli standard del progetto**: convenzioni di naming, logging, gestione errori, eventi, test e configurazione.

Questa sarà la nostra "versione 0.2 dell'architettura". Da quel momento in poi ogni nuova funzionalità (LanceDB, Browser Engine, Computer Engine, memoria, multi-agente) si innesterà su fondamenta già stabili, riducendo al minimo il refactoring futuro.

È un investimento iniziale che, per un progetto con l'ambizione del tuo, ritengo molto più vantaggioso che continuare ad aggiungere componenti su una struttura ancora in evoluzione.

# La filosofia

Vorrei che il progetto rispettasse sempre questi dieci principi.

## 1. Local First

Il sistema deve funzionare completamente offline.

Internet deve essere un'opzione.

Mai un requisito.

---

## 2. Modularità

Ogni componente deve poter essere sostituito.

Ollama.

LanceDB.

Browser.

OCR.

Tutto.

---

## 3. Event Driven

Ogni operazione produce eventi.

Mai chiamate "nascoste".

---

## 4. Plugin First

Ogni funzionalità importante deve poter diventare un plugin.

---

## 5. Security by Design

La sicurezza non sarà aggiunta dopo.

Sarà parte dell'architettura.

---

## 6. Test First

Ogni componente nasce con i test.

---

## 7. API First

Ogni componente deve poter essere usato:

* dalla CLI;
* dalla WebUI;
* da un'altra applicazione.

---

## 8. Observable

Ogni azione deve essere osservabile.

Log.

Metriche.

Timeline.

Eventi.

---

## 9. Reproducible

L'intero sistema deve poter essere ricreato con:

```
git clone

podman compose up
```

e basta.

---

## 10. Replaceable

Se una tecnologia sparisce domani, il progetto continua a vivere.

Questo principio guiderà tutte le nostre decisioni.

```text
funzionalità.

Tutti i package, documenti, repository e riferimenti futuri
utilizzeranno RumiAI come identità del progetto.
```

# creami degli script sh posix compliant per la generazione di questi file
--------------------------------------------------------------------------------

Perfetto. Procediamo in modo coerente con la filosofia di RumiAI: invece di creare manualmente la struttura, prepariamo degli script riproducibili.

Per questa fase creeremo **solo gli script di bootstrap della Foundation Release**, senza ancora generare contenuti definitivi dei documenti.

La struttura sarà:

```text
rumiai/
└── scripts/
    └── foundation/
        ├── 00-create-structure.sh
        └── 01-create-foundation-docs.sh
```

Gli script saranno:

* POSIX `sh` compatibili;
* senza dipendenze esterne;
* eseguibili sia su Linux host sia dentro container;
* idempotenti (rieseguibili senza distruggere dati esistenti).

---

## Script 1 — Creazione struttura repository

File:

```text
scripts/foundation/00-create-structure.sh
```

```sh
#!/bin/sh
#
# RumiAI Foundation Release
# Create project structure
#
# POSIX compliant
#

set -eu

PROJECT_ROOT=${1:-rumiai}

echo "Creating RumiAI project structure in: $PROJECT_ROOT"

mkdir -p "$PROJECT_ROOT"

cd "$PROJECT_ROOT"

DIRECTORIES="
app
docs
docs/architecture
docs/decisions
docs/specifications
docs/security
docs/roadmap
tests
scripts
scripts/foundation
configs
plugins
examples
data
workspace
"

for dir in $DIRECTORIES
do
    mkdir -p "$dir"
    echo "created: $dir"
done

FILES="
README.md
LICENSE
CHANGELOG.md
"

for file in $FILES
do
    if [ ! -f "$file" ]; then
        touch "$file"
        echo "created: $file"
    else
        echo "exists: $file"
    fi
done

echo ""
echo "RumiAI foundation structure created."
```

## Script 2 — Creazione documentazione Foundation Release

File:

```text
scripts/foundation/01-create-foundation-docs.sh
```

```sh
#!/bin/sh
#
# RumiAI Foundation Release
# Create documentation skeleton
#
# POSIX compliant
#

set -eu

DOC_ROOT=${1:-docs}

echo "Creating RumiAI documentation skeleton"

mkdir -p \
"$DOC_ROOT/architecture" \
"$DOC_ROOT/decisions" \
"$DOC_ROOT/specifications" \
"$DOC_ROOT/security" \
"$DOC_ROOT/roadmap"


create_file()
{
    FILE="$1"

    if [ ! -f "$FILE" ]; then
        cat > "$FILE" <<EOF
# $(basename "$FILE" .md)

RumiAI Project Documentation

Status:
Draft

EOF
        echo "created: $FILE"
    else
        echo "exists: $FILE"
    fi
}


create_file "$DOC_ROOT/00-project-manifesto.md"

create_file "$DOC_ROOT/architecture/software-architecture-document.md"

create_file "$DOC_ROOT/specifications/kernel.md"

create_file "$DOC_ROOT/specifications/knowledge.md"

create_file "$DOC_ROOT/specifications/tool.md"

create_file "$DOC_ROOT/specifications/llm.md"

create_file "$DOC_ROOT/specifications/memory.md"

create_file "$DOC_ROOT/specifications/workflow.md"

create_file "$DOC_ROOT/specifications/browser.md"

create_file "$DOC_ROOT/specifications/computer.md"

create_file "$DOC_ROOT/specifications/security.md"

create_file "$DOC_ROOT/security/security-model.md"

create_file "$DOC_ROOT/development-standards.md"

create_file "$DOC_ROOT/testing-strategy.md"

create_file "$DOC_ROOT/roadmap/roadmap.md"


create_file "$DOC_ROOT/decisions/ADR-0000-project-identity.md"
create_file "$DOC_ROOT/decisions/ADR-0001-local-first.md"
create_file "$DOC_ROOT/decisions/ADR-0002-podman-runtime.md"
create_file "$DOC_ROOT/decisions/ADR-0003-plugin-architecture.md"
create_file "$DOC_ROOT/decisions/ADR-0004-event-driven-architecture.md"
create_file "$DOC_ROOT/decisions/ADR-0005-knowledge-abstraction.md"
create_file "$DOC_ROOT/decisions/ADR-0006-lancedb-initial-store.md"
create_file "$DOC_ROOT/decisions/ADR-0007-llm-provider-abstraction.md"


echo ""
echo "RumiAI documentation skeleton created."
```

## Installazione

Dalla directory dove vuoi creare il progetto:

```sh
mkdir -p scripts/foundation
```

copi i due file:

```text
scripts/foundation/00-create-structure.sh
scripts/foundation/01-create-foundation-docs.sh
```

poi:

```sh
chmod +x scripts/foundation/*.sh
```
