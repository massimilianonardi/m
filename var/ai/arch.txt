# Criteri di completamento della Fase 1

Considererei conclusa questa fase quando il sistema soddisfa questi requisiti:

* **Separazione delle responsabilità**: il codice che parla con Ollama, il planner, il dispatcher e i tool sono moduli distinti.
* **Tool intercambiabili**: aggiungere un nuovo tool richiede solo implementare l'interfaccia comune e registrarlo, senza modificare il core dell'agente.
* **Flusso completo funzionante**: almeno una richiesta attraversa correttamente Planner → Dispatcher → Tool → LLM → Risposta.
* **Test automatizzati di base**: almeno alcuni casi verificano il comportamento del planner e del dispatcher.
* **Logging leggibile**: ogni passaggio principale è tracciato.

Una volta raggiunti questi obiettivi, avrai una base solida su cui costruire le fasi successive. Il **TerminalTool**, il **BrowserTool**, il **RAG** e il **Computer Use** diventeranno semplicemente nuovi moduli che sfruttano la stessa infrastruttura, invece di richiedere modifiche al cuore dell'agente.

--------------------------------------------------------------------------------
La variante è quella che sceglierei anch'io per un progetto destinato a crescere.

Tuttavia **non ti consiglierei uno script Bash monolitico** che genera decine di file Python con centinaia di righe di `cat <<EOF`. Diventa difficile da mantenere e ogni modifica richiede di rigenerare tutto.

Per un progetto come il tuo farei invece un **bootstrap POSIX** che:

* crea la struttura del progetto;
* crea gli ambienti (`backend`, `tests`, `tools`, ecc.);
* genera solo i file minimi (`pyproject.toml`, `.env.example`, `requirements.txt`, `Dockerfile`, `Containerfile`, ecc.);
* copia il codice Python da template versionati.

In questo modo il bootstrap rimane di poche decine di righe e il codice Python vive in file normali, dove puoi usare il tuo editor, Git e i test.

Se invece lo script deve **contenere tutto il codice della Fase 1**, il risultato supera facilmente **800–1200 righe**, perché deve generare:

* struttura del progetto;
* `pyproject.toml`;
* `requirements.txt`;
* `config.py`;
* logging;
* FastAPI;
* client Ollama;
* Agent Core;
* Planner;
* Dispatcher;
* Registry;
* Tool base;
* TimeTool;
* modelli Pydantic;
* API `/chat`;
* test `pytest`;
* `.gitignore`;
* `.env.example`;
* script di avvio;
* documentazione iniziale.

Una risposta di queste dimensioni supera il limite di lunghezza che posso inviare in un singolo messaggio.

### Ti propongo un approccio che ritengo più pratico

Costruiamo insieme un **bootstrap professionale** in più passi, ognuno eseguibile e testabile.

1. **bootstrap.sh** (≈150 righe, POSIX puro)

   * crea tutta la struttura del progetto;
   * genera i file di configurazione;
   * crea l'ambiente iniziale.

2. **templates.tar** (ricreato come parte della conversazione)

   * contiene tutto il codice Python della Fase 1.

3. Ad ogni passo esegui i test prima di proseguire.

In questo modo avrai un progetto realmente mantenibile, invece di un enorme script Bash difficile da aggiornare.

Ritengo che questa soluzione sia la più adatta per un progetto ambizioso come il tuo, che vuoi sviluppare in modo incrementale e con verifiche ad ogni fase.

## Perché questa suddivisione

Ogni fase richiederà circa 100–200 righe di codice. Questo ha diversi vantaggi:

* il codice è facile da leggere e modificare;
* puoi eseguire test dopo ogni passo;
* se qualcosa non funziona, è immediato capire dove intervenire.

## Una scelta architetturale che farei subito

C'è un aspetto che farei **prima ancora di scrivere una riga di codice**: progettare il sistema come un insieme di **servizi indipendenti**, non come un unico programma.

Ad esempio:

```text
OpenWebUI
      │
      ▼
 FastAPI (Agent)
      │
 ┌────┴────┐
 │         │
 ▼         ▼
Ollama   Tool Engine
             │
   ┌─────────┼─────────┐
   ▼         ▼         ▼
Filesystem Browser   RAG
```

In questa architettura:

* **FastAPI** espone l'API dell'agente.
* **Agent Core** decide cosa fare.
* **Tool Engine** esegue gli strumenti.
* **Ollama** si occupa esclusivamente dell'inferenza del modello.

Questa separazione rende molto più semplice aggiungere in seguito funzionalità come Computer Use, Browser Automation, RAG o persino modelli diversi senza modificare il cuore del sistema.

### Una nota sui test

Per ogni fase prepareremo anche uno script di test (`scripts/test_phase_X.sh` oppure test con `pytest`) in modo da verificare subito che il componente appena aggiunto funzioni prima di passare alla fase successiva. Questo approccio riduce molto il rischio di accumulare problemi nascosti che emergono solo quando il progetto diventa più complesso.

# Una proposta aggiuntiva

Vorrei fare una cosa che raramente si vede nei tutorial ma che, secondo me, ti sarà molto utile: ogni script sarà accompagnato da una breve spiegazione dell'architettura e del motivo delle scelte fatte. In questo modo non avrai solo un progetto funzionante, ma anche una comprensione chiara di come si evolve.

Inoltre, manterremo un principio importante: **nessuno script modificherà file creati dagli script precedenti**, salvo casi eccezionali e dichiarati. Ogni fase aggiungerà nuovi componenti senza rompere quelli esistenti, così potrai tornare facilmente indietro o confrontare le modifiche con Git.

Mi piace molto questo metodo di lavoro: è incrementale, verificabile e produce una base solida su cui costruire un agente locale complesso. Quando mi scriverai **"avanti"**, inizieremo con `01-bootstrap.sh`.

Quello che descrivi è molto simile a un framework per agenti, più che a una semplice applicazione che interroga un LLM. La scelta di procedere per piccoli passi con test incrementali è probabilmente quella che ti farà risparmiare più tempo: ogni nuova capacità introduce nuovi punti di errore e isolarli rende il debug molto più semplice.

## La roadmap che seguirei

Se il tuo obiettivo finale è un assistente locale paragonabile a quelli più evoluti, procederei in quest'ordine:

1. **Client Ollama** ben incapsulato (senza più `ask.py`).
2. **Agent Core** con gestione di messaggi, prompt e stato della conversazione.
3. **Sistema di tool** (registry + dispatcher), con un primo tool molto semplice per validare il flusso.
4. **Tool Filesystem** e **Tool Terminal**, limitando inizialmente i comandi consentiti.
5. **Browser automation** con Playwright.
6. **RAG** (loader, chunking, embeddings e retrieval).
7. **Memoria persistente** (cronologia e memoria semantica).
8. **Planner** capace di concatenare più tool nella stessa richiesta.
9. **Computer Use**, che richiede un ciclo di osservazione (screenshot) → ragionamento → azione → nuova osservazione.

Questa sequenza ti permette di verificare ogni componente prima di introdurre il successivo. In particolare, il sistema di tool è la base comune su cui si appoggeranno terminale, browser, RAG e Computer Use: se progetti bene quella parte, aggiungere nuove capacità diventerà soprattutto una questione di implementare nuovi moduli anziché modificare il cuore dell'agente.

# Criteri di completamento della Fase 1

Considererei conclusa questa fase quando il sistema soddisfa questi requisiti:

* **Separazione delle responsabilità**: il codice che parla con Ollama, il planner, il dispatcher e i tool sono moduli distinti.
* **Tool intercambiabili**: aggiungere un nuovo tool richiede solo implementare l'interfaccia comune e registrarlo, senza modificare il core dell'agente.
* **Flusso completo funzionante**: almeno una richiesta attraversa correttamente Planner → Dispatcher → Tool → LLM → Risposta.
* **Test automatizzati di base**: almeno alcuni casi verificano il comportamento del planner e del dispatcher.
* **Logging leggibile**: ogni passaggio principale è tracciato.

Una volta raggiunti questi obiettivi, avrai una base solida su cui costruire le fasi successive. Il **TerminalTool**, il **BrowserTool**, il **RAG** e il **Computer Use** diventeranno semplicemente nuovi moduli che sfruttano la stessa infrastruttura, invece di richiedere modifiche al cuore dell'agente.

# Visione del progetto

L'obiettivo è realizzare una piattaforma completamente locale, open source e modulare, in grado di eseguire agenti AI autonomi senza dipendere da servizi cloud.

L'intero sistema deve essere progettato secondo alcuni principi fondamentali:

* **modularità**, ogni componente deve poter essere sostituito senza modificare il resto del sistema;
* **sicurezza**, ogni capacità operativa dell'agente deve essere controllata e limitata da policy;
* **estendibilità**, nuove funzionalità devono poter essere aggiunte come plugin o moduli;
* **osservabilità**, ogni azione dell'agente deve poter essere tracciata e analizzata;
* **portabilità**, tutto il sistema deve poter essere eseguito localmente tramite Podman.

# Sottosistemi

L'intero progetto sarà composto da sei sottosistemi principali.

---

## 1. Presentation Layer

È il livello con cui interagisce l'utente.

Non contiene alcuna logica AI.

Può essere sostituito senza modificare il resto del sistema.

Supporterà:

* Open WebUI
* CLI
* REST API
* MCP
* futura interfaccia desktop
* futura applicazione mobile

Riceve una richiesta e la inoltra all'Agent Engine.

---

## 2. Agent Engine

È il cervello del sistema.

Non conosce i dettagli tecnici dei tool o del database vettoriale.

Contiene:

```text
Planner
Executor
Workflow Engine
Conversation Manager
Memory Manager
Event Manager
```

### Planner

Riceve la richiesta dell'utente.

Decide:

* quali tool usare;
* se interrogare la knowledge base;
* se interrogare la memoria;
* se rispondere direttamente.

Non esegue nulla.

Produce un piano.

---

### Executor

Riceve il piano.

Esegue le operazioni nell'ordine previsto.

Ad esempio:

```text
1 Browser

↓

2 Filesystem

↓

3 Terminal

↓

4 LLM
```

L'Executor è l'unico componente autorizzato ad eseguire azioni.

---

### Workflow Engine

Permette di costruire workflow multi-step.

Esempio:

```text
Apri browser

↓

Scarica PDF

↓

Indicizza documento

↓

Aggiorna memoria

↓

Rispondi
```

---

### Memory Manager

Gestisce la memoria dell'agente.

Non è il RAG.

È la memoria dell'agente.

Ad esempio:

* preferenze dell'utente;
* conversazioni;
* fatti importanti;
* cronologia.

---

### Event Manager

Ogni operazione genera eventi.

Ad esempio:

```text
ToolStarted

ToolCompleted

DocumentIndexed

SearchExecuted

MemoryUpdated
```

Gli eventi potranno essere usati per:

* log;
* audit;
* debugging;
* statistiche.

---

# 3. Tool Engine

È il sottosistema che permette all'agente di agire.

Ogni tool implementa la stessa interfaccia.

```text
Tool

↓

ToolResult
```

Ogni tool restituisce sempre:

```text
success

output

metadata

execution_time

error
```

I tool previsti sono:

```text
TerminalTool

FilesystemTool

BrowserTool

ComputerTool

GitTool

ContainerTool

NetworkTool

PythonTool

NotificationTool
```

Ogni tool sarà completamente indipendente dagli altri.

---

# 4. Knowledge Engine

È il motore della conoscenza.

Non contiene logica di conversazione.

Gestisce esclusivamente documenti.

La pipeline sarà:

```text
Documento

↓

Loader

↓

Preprocessor

↓

Chunker

↓

Embedding Engine

↓

Knowledge Store

↓

Retriever

↓

Reranker

↓

Context Builder
```

---

## Loader

Carica documenti.

Supporterà:

* txt
* markdown
* pdf
* docx
* html
* epub
* codice sorgente
* repository Git

---

## Preprocessor

Normalizza il testo.

Ad esempio:

* unicode;
* CRLF;
* markdown;
* html;
* OCR.

---

## Chunker

Divide i documenti.

Supporterà:

* chunk fissi;
* chunk semantici;
* chunk gerarchici.

---

## Embedding Engine

Genera gli embeddings.

Il modello sarà configurabile.

Potremo usare:

* Sentence Transformers;
* Ollama embeddings;
* modelli futuri.

---

## Knowledge Store

È un'interfaccia.

L'agente non saprà mai quale database utilizziamo.

Implementazioni previste:

```text
LanceDB

Qdrant

FAISS

ChromaDB
```

---

## Retriever

Esegue la ricerca semantica.

---

## Reranker

Ordina i risultati.

---

## Context Builder

Costruisce il contesto che verrà inviato al modello.

---

# 5. LLM Engine

È l'interfaccia verso il modello linguistico.

Non dipende da Ollama.

Espone operazioni come:

```text
generate()

stream()

embedding()

tokenize()
```

Backend possibili:

* Ollama
* llama.cpp
* vLLM
* futuri provider

---

# 6. Infrastructure Layer

È il livello più basso.

Contiene:

```text
Podman

Filesystem

Rete

Configurazione

Logging

Secrets

Volumes
```

È l'unico livello che conosce il sistema operativo.

---

# Sicurezza

Ogni operazione dell'agente passerà attraverso un sistema di policy.

```text
Planner

↓

Executor

↓

Policy Engine

↓

Tool
```

Le policy potranno decidere:

* se un comando è consentito;
* se è necessaria conferma;
* se deve essere registrato;
* se è vietato.

# Evoluzione futura

Questa architettura è pensata per crescere in modo incrementale.

Nel breve periodo ci concentreremo su:

* rifattorizzazione verso la nuova struttura;
* introduzione del Knowledge Engine;
* integrazione con LanceDB;
* completamento del primo ciclo RAG.

Successivamente potremo sviluppare:

* Browser Engine basato su Playwright;
* Computer Engine per mouse, tastiera e screenshot;
* GitTool e ContainerTool dedicati;
* Workflow Engine multi-step;
* memoria persistente a lungo termine;
* supporto a più modelli LLM;
* plugin e integrazione MCP.

---

## Una proposta aggiuntiva

C'è un'ultima idea che vorrei introdurre, perché credo che possa fare la differenza nel lungo periodo.

Vorrei trattare l'intero progetto come un **micro-kernel**: il nucleo si occupa solo di orchestrare pianificazione, esecuzione, eventi e sicurezza, mentre tutte le capacità (tool, knowledge store, browser, memoria, LLM, workflow) diventano moduli con interfacce ben definite. Questo approccio ti consentirà di aggiungere o sostituire componenti senza impatti sul resto del sistema e renderà molto più semplice sperimentare tecnologie nuove, come LanceDB, nuovi modelli di embedding o un diverso motore di browser automation, mantenendo stabile il cuore della piattaforma. È una scelta che richiede un po' più di disciplina progettuale all'inizio, ma che ripaga quando il progetto cresce.
